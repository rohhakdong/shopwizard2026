# 운영 배포 체크리스트 — 실결제 검증 · 설정

> 이 문서는 "운영 반영 전 DDL/보정 SQL/토스 키 교체"(별도 목록) 외에, **실결제 경로 검증(1번)**, **설정 함정(2번)**, **NHN KCP 운영 전환(3번)** 을 정리한 것이다.
> 값(비밀번호·키·호스트)은 이 문서에 적지 않는다. 환경변수/배포 설정으로만 준다.
>
> **PG 구성**: 결제는 `PaymentGateway` 뒤에 숨어 있고 `PAYMENT_ENABLED_PGS` 로 켜는 PG 를 정한다(기본값 `TOSS`, KCP 만 쓰면 `KCP`, 병행이면 `KCP,TOSS`).
> 1번은 토스 중심으로 쓰인 내용이라 PG 별로 읽고, KCP 는 3번을 따른다. 이미 결제된 주문의 환불·웹훅은 PG 를 꺼도 그 PG 로 처리된다.

---

## 1. 실결제 경로 검증 + 대사(정합성 확인)

### 왜 필요한가
- 토스 승인(`/order/checkout` → 토스 confirm)부터 주문 저장까지의 **전체 경로는 개발 환경에서 끝까지 돌려 보지 못했다**
  (샌드박스 key-in 결제는 바로 "완료" 상태가 되어 서버의 승인 호출이 실패한다). 단위 테스트와 부분 라이브만 검증됨.
- 승인은 됐는데 주문 저장 전에 서버가 죽거나 응답이 끊기면 자동 취소(보상)가 돌지 못해 **돈만 결제된 건**이 남을 수 있다.
  이런 건을 찾아내는 자동 대사 작업은 없다 → 아래 수동 대사를 주기적으로 한다.

### 1-A. 첫 결제 리허설 (운영 키 적용 직후, 소액 상품으로)
공통: 시작 전 해당 상품의 재고(`tPrdProd.SupplyQty`)와 판매가를 메모해 둔다.

| # | 시나리오 | 확인할 것 | 결과 |
|---|---|---|---|
| 1 | 비회원, 신용카드, 소액 상품 1개 | 결제 완료 화면 → `tOrdOrder`/`tOrdOrderProd`/`tOrdOrderPay`/`tOrdOrderPayLogToss` 각 1건, 주문상태 `지불완료`, 재고 1 감소, `tOrdOrderProdStockLog` DEDUCT 1건 | ☐ |
| 2 | 회원 로그인, 장바구니 → 2개 이상 상품(옵션 상품 포함) | 주문서의 상품금액+배송비 = 결제창 금액 = `PayAmt`, 라인별 `SalePrice`·`NvPrice`·`ReciptAmt` 가 **수량이 곱해진 합계** | ☐ |
| 3 | 선불 배송비 상품 | 배송비(상점별 최대값 합산)가 결제 총액에 포함, 라인에는 기록 안 됨(정상) | ☐ |
| 4 | 가상계좌 (토스) | 주문 `주문접수`, 재고는 즉시 차감, 입금 후 웹훅으로 `지불완료` 전환 (KCP 가상계좌는 3-D 참고) | ☐ |
| 5 | 결제창에서 취소/닫기 | 주문·재고 변화 없음, 주문서 복원 | ☐ |
| 6 | 주문취소접수(관리자 화면) | 토스 결제 취소 + 재고 복원(+수량), 이중 취소해도 재고가 두 번 늘지 않음 | ☐ |
| 7 | 토스 대시보드에서 결제 취소(웹훅 `CANCELED`) | 배송 전 라인만 `주문취소`, 재고 복원 | ☐ |
| 8 | 재고 부족 | 재고 1인 상품을 2개 주문 → 주문서 단계에서 "재고가 부족합니다", 결제창 안 열림 | ☐ |

리허설 후: 테스트 주문은 취소(토스 취소 포함)하고 재고가 원래 값인지 확인한다.

### 1-B. 토스 웹훅 등록 확인
- [ ] 토스 개발자센터(운영 상점)에 웹훅 URL 등록: `https://<운영도메인>/payment/webhook/toss`, 이벤트 `PAYMENT_STATUS_CHANGED`
- [ ] `/payment/**` 는 로그인 없이 열려 있어야 한다(인증 제외 경로 — 이미 설정됨). 방화벽/WAF 가 토스 서버 요청을 막지 않는지 확인
- [ ] 웹훅 본문은 신뢰하지 않고 서버가 토스 API 로 결제 상태를 다시 조회한다(위조 요청으로는 상태 동기화만 일어남)

### 1-C. 정기 대사 (운영 시작 후 매일 → 안정되면 주 1회)
**목적**: 토스에서는 승인됐는데 우리 주문이 없는 건(또는 반대)을 찾는다.

1. 토스 대시보드 → 결제내역 → 전일 승인 건 내려받기(엑셀): 결제키(paymentKey), 주문ID, 금액, 상태
2. 우리 DB 의 같은 기간 결제 건을 뽑아 비교한다:
```sql
-- 전일 스토어프론트 결제 (PgTradeNo = 토스 paymentKey, PgOrderCode = 토스 orderId)
SELECT P.OrderNo, P.PgTradeNo, P.PgOrderCode, P.PayAmt, P.PayDate, O.OrderState
FROM shopion.tOrdOrderPay P
JOIN shopion.tOrdOrder O ON O.OrderNo = P.OrderNo
WHERE P.PgCode = 'TOSS'
  AND P.PayDate >= CURDATE() - INTERVAL 1 DAY AND P.PayDate < CURDATE()
ORDER BY P.PayDate;
```
3. 판정
   - 토스에 있고(상태 DONE) DB 에 없다 → **결제만 된 건**: 고객에게 안내 후 토스에서 수동 취소(또는 주문 수기 등록)
   - DB 에 있고 토스에는 취소(CANCELED)로 되어 있는데 주문 상태가 `주문취소`/`환불완료`가 아니다 → 웹훅 누락: 해당 건의 취소 처리
   - 금액 불일치 → 즉시 원인 확인(정상이라면 발생하지 않음 — 서버가 금액을 계산·검증한다)
4. 로그: `주문 저장 실패로 인한 자동 취소` 가 호출된 건은 서버 로그에서 확인(저장 실패 → 자동 취소 정상 동작 사례)

### 1-D. 이상 징후 모니터링 쿼리
```sql
-- 결제는 됐는데(지불완료) 라인이 비어 있는 주문
SELECT O.OrderNo FROM shopion.tOrdOrder O
LEFT JOIN shopion.tOrdOrderProd OP ON OP.OrderNo = O.OrderNo
WHERE O.OrderState = '지불완료' AND OP.OrderNo IS NULL;

-- 재고가 음수가 된 상품(샵링커/상품매칭은 초과 차감 허용 — 스토어프론트는 막힘)
SELECT ProdCode, ProdName, SupplyQty FROM shopion.tPrdProd WHERE SupplyQty < 0;

-- 차감 이력은 있는데 주문 라인이 없는 이력(롤백 누락 징후 — 정상이면 0건)
SELECT L.OrderNo, L.OrderProdNo FROM shopion.tOrdOrderProdStockLog L
LEFT JOIN shopion.tOrdOrderProd OP ON OP.OrderNo = L.OrderNo AND OP.OrderProdNo = L.OrderProdNo
WHERE OP.OrderNo IS NULL;
```

### 1-E. 운영 시작 방식 권장
- 첫 주는 저가 상품/소수 고객으로 시작, 매일 1-C 대사 수행
- 첫 정산 마감은 소량 상점·짧은 기간으로(마감은 앱에서 되돌릴 수 없음)

## 2. 설정 함정 (배포 설정)

### 2-A. 필수 환경변수 / 설정
| 항목 | 설정 | 안 하면 |
|---|---|---|
| 프로파일 | `SPRING_PROFILES_ACTIVE=prod` (기본값은 `dev`) | MyBatis **DEBUG 로그에 SQL 파라미터·고객정보** 가 찍힘, 템플릿 캐시 꺼짐, 커넥션 풀 10 |
| `DB_HOST`, `DB_PASSWORD` | 배포 설정으로 주입(저장소에 없음) | 기동 실패 |
| `SESSION_COOKIE_SECURE` | HTTPS 서비스면 `true` (기본 `false`) | 세션 쿠키가 HTTP 로도 전송됨 |
| `PAYMENT_ENABLED_PGS` | 쓸 PG (`TOSS` 기본 / `KCP` / `KCP,TOSS`), 필요하면 `PAYMENT_DEFAULT_PG` | 미설정이면 **토스만** 켜짐 → KCP 만 계약했다면 반드시 `KCP` 로 설정 |
| `TOSS_SECRET_KEY`, `TOSS_CLIENT_KEY` | **운영 시크릿 키 / 운영 클라이언트 키** (둘 다 환경변수, 기본값은 테스트 키). 화면은 `/payment/config` 로 클라이언트 키를 받는다 | 미설정 시 **조용히 테스트 키로 동작** → 운영 결제 승인 실패/혼선. 둘 중 하나만 바꾸면 결제창/승인 키 불일치. 토스를 안 쓰면 `PAYMENT_ENABLED_PGS` 에서 빼서 결제수단에도 안 보이게 한다 |
| `KCP_*` | NHN KCP 설정 일체 — **3-A 참고** | 인증서·키·검증키가 없거나 틀리면 기동 실패(운영) |
| `UPLOAD_DIR` | 영구 저장소의 **절대경로** (기본 `uploads` 는 실행 위치 기준 상대경로) | 서버 위치가 바뀌면 이미지가 사라진 것처럼 보임, 백업 대상 누락 |
| `SHOP_CHNL_CODE` | 운영 DB 의 스토어프론트 채널코드 (기본 `1208674775Z2`) | 주문이 엉뚱한 채널로 저장 |
| `SHOPLINKER_*` | 필요 시(기본값은 운영 주소 http) | — |

### 2-B. 권한·보안 설정
- [ ] `app.authz.mode` 는 기본 `enforce` — **`off`/`log` 로 바꾸지 말 것**(off 면 역할 권한·데이터 범위 검사가 모두 꺼짐)
- [ ] HTTPS 종단(리버스 프록시/로드밸런서) 사용 시 클라이언트 IP 전달 확인 — 로그인 시도 제한 키가 (종류+아이디+접속 IP)인데 앱은 `getRemoteAddr()` 를 쓰고 `server.forward-headers-strategy` 가 설정돼 있지 않다.
      프록시 뒤에서 모든 접속이 같은 IP 로 보이면, 특정 아이디에 대한 실패 시도가 **그 아이디의 모든 사용자를 잠글 수 있다**. 프록시를 쓰면 `server.forward-headers-strategy=native`(또는 framework) 설정을 검토
- [ ] 배포 후 **전체 권한 계정(시스템 관리자)은 재로그인** — 서비스 범위 제한이 들어가면서 기존 세션은 제한이 걸린 상태로 보임
- [ ] 기존 로그인 중이던 관리자/고객 세션은 서버 재시작 시 모두 끊김(세션이 서버 메모리) → 사용량이 적은 시간대에 배포

### 2-C. 운영 환경 특성
- [ ] **서버는 1대 기준**: 세션, 로그인 시도 제한, 샵링커 수집 중복 실행 방지, **KCP 가상계좌 만료 잡**(10분 주기)이 서버 메모리/단일 실행을 전제한다. 2대 이상이면 세션 공유(sticky/세션 저장소)와 수집·만료 잡의 단일 실행 보장이 필요
      (만료 잡은 상태 조건부 갱신과 행 잠금으로 이중 처리는 막지만, 두 대가 동시에 KCP 를 호출하는 것은 피해야 한다)
- [ ] 업로드 이미지 디렉터리 쓰기 권한/용량/백업, 이미지 URL 은 `/images/**`
- [ ] 샵링커 주문수집 API 는 `http://` (제공 측 사양) — 서버에서 해당 호스트로 나가는 방화벽 허용 확인
- [ ] 운영 DB 사전 점검: 별도 목록(DDL `tOrdOrderProdStockLog`, 옵션가 NULL 보정 SQL, 정산 컬럼 존재 확인)
- [ ] 기동 로그에 `spring.profiles.active=prod` 가 보이는지, 로그에 SQL 파라미터가 안 찍히는지 확인

### 2-D. 배포 직후 스모크 테스트 (10분)
- [ ] 관리자 로그인 → 사이드바 메뉴가 역할대로 보임(시스템 관리자 전체, 업체담당자 제한)
- [ ] 주문관리 화면 조회(기간 지정), 판매 상품 관리 조회
- [ ] 업체담당자 계정으로 로그인 → 자기 상점 주문만 보이는지
- [ ] 스토어프론트: 상품 목록 → 상세 → 바로구매 → 주문서 금액 표시 → (소액 결제는 1-A 리허설로)
- [ ] 고객 로그인(기존 고객 1명) — 첫 로그인 때 비밀번호 해시가 BCrypt 로 자동 전환됨(`tPrfCust.Passwd` 가 `$2` 로 시작)
- [ ] 서버 로그에 ERROR/WARN 폭주가 없는지

## 3. NHN KCP 운영 전환

KCP 는 토스와 달리 **서버 IP · 서비스 인증서 · 웹훅 URL** 을 파트너관리자에 등록해야 하고, 가상계좌 입금은 **웹훅으로만** 알 수 있다.
개발 환경(`KCP_MODE=test`, 사이트코드 `T0000`, KCP 공용 샘플 인증서)에서는 실결제가 일어나지 않는다. 운영은 발급받은 사이트코드·인증서로 실결제가 된다.

### 3-A. 설정 (환경변수 — 값은 저장소·로그·화면에 남기지 않는다)
| 항목 | 값 | 비고 |
|---|---|---|
| `PAYMENT_ENABLED_PGS` | `KCP` (토스 병행이면 `KCP,TOSS`) | 기본값은 `TOSS` |
| `KCP_MODE` | `prod` | 기본 `test`. `prod` 에서 테스트 사이트코드(`T0000`)를 쓰면 기동 거부 |
| `KCP_SITE_CD` | 운영 사이트코드(영문 대문자·숫자 5자리) | 형식이 틀리면 기동 거부 |
| `KCP_SITE_NAME` | 상점명 | 결제창에 표시 |
| `KCP_CERT_PATH` | 서비스 인증서(PEM) 파일 경로 | **저장소 밖** 경로. 서버 실행 계정만 읽게 권한 제한 |
| `KCP_PRIVATE_KEY_PATH` | 개인키(PKCS8 PEM) 파일 경로 | **저장소 밖**. 안전한 곳에 백업 |
| `KCP_PRIVATE_KEY_PASSWORD` | 개인키 비밀번호 | 환경변수로만. 틀리면 기동 실패 |
| `KCP_WEBHOOK_KEY` | 파트너관리자 웹훅관리의 **운영 검증키** | **운영에서 없으면 기동 거부** |
| `KCP_PUBLIC_BASE_URL` | `https://<운영도메인>` | 모바일 결제 복귀(Ret_URL) 기준 주소. KCP 가 https 를 요구한다. **리버스 프록시 뒤라면 반드시 지정**(비우면 요청이 들어온 주소를 쓴다) |
| `KCP_WEBHOOK_ALLOWED_IPS` | (비움 권장) | 비우면 운영 KCP 발신 IP 3개 |
| `KCP_WEBHOOK_TRUST_FORWARDED` | 프록시 뒤에서만 `true` | 3-C 참고 |
| `KCP_VA_EXPIRE_MINUTES` | 기본 `4320`(72시간) | 가상계좌 입금 마감까지의 시간 |
| `KCP_VA_EXPIRE_GRACE_MINUTES` | 기본 `60` | 마감 후 만료 처리까지의 여유(마감 직전 입금과의 경합 방지) |
| `KCP_VA_EXPIRE_JOB_ENABLED` | 기본 `true` | 만료 잡 켜기/끄기(주기는 10분) |

- 개인키는 **재발급본**을 쓰는 것을 권장한다(취급 중 외부에 노출됐을 가능성이 있는 키는 폐기). 인증서·개인키·비밀번호·검증키는 채팅·이슈·로그에 붙이지 않는다.
- 기동 로그에서 KCP 설정 점검(인증서·키·비밀번호·사이트코드·검증키)이 통과해 서버가 올라오는지 확인한다.

### 3-B. 파트너관리자 등록
- [ ] 서비스 인증서(인증센터) 발급·다운로드, 개인키 비밀번호 보관
- [ ] **결제 서버 아이피 설정**에 운영 서버의 **고정 공인 IP** 등록(서버 IP 가 바뀌면 재등록). 개발 환경에서는 이 설정이 승인 호출에 필요한지 확정하지 못했으므로(인증서 직렬화 오류와 같은 증상이 나왔다) 등록해 두는 것을 권장
- [ ] 기술관리센터 > 웹훅(Webhook)관리: 웹훅 URL `https://<운영도메인>/payment/webhook/kcp` 등록(**https 필수**), 운영 **검증키** 발급·조회
- [ ] 계약된 결제수단(카드·계좌이체·**가상계좌**·간편결제)과 사이트코드 확인. 가상계좌가 계약에 없으면 발급이 거절된다

### 3-C. 네트워크 · 프록시
- **서버 → KCP**(아웃바운드, TLS 1.2+): `spl.kcp.co.kr`(승인·취소·조회·가상계좌), `smpay.kcp.co.kr`(모바일 거래등록). 브라우저는 결제창을 `spay.kcp.co.kr` 에서 불러온다. KCP 는 초당 10회 이상 호출하면 IP 를 차단할 수 있어 앱이 호출 사이에 간격을 둔다.
- **KCP → 서버**(인바운드, 웹훅): 출발지 `103.215.144.173`, `103.215.144.174`, `210.122.72.173` 를 방화벽/WAF 에서 허용한다. 앱도 이 IP 의 요청만 받는다(아니면 403).
- **리버스 프록시/로드밸런서 뒤**: 앱이 보는 접속 IP 가 프록시 IP 가 되므로 `KCP_WEBHOOK_TRUST_FORWARDED=true` 가 필요하다. 이때 앱은 `X-Forwarded-For` 의 **첫 번째 값**을 믿으므로,
  프록시가 클라이언트가 보낸 헤더를 **덮어쓰도록**(덧붙이기가 아니라 교체) 구성해야 한다. 아니면 외부에서 헤더를 위조해 IP 검사를 통과할 수 있다.
  (IP 검사 하나로 지불완료가 되지는 않는다 — 웹훅은 해시 검증과 KCP 거래조회 재확인을 거친다.)
- 모바일 결제 복귀 주소(`/payment/kcp/return`)는 KCP 결제창이 **브라우저를 통해** 호출하므로 인터넷에서 닿는 https 주소여야 한다(`KCP_PUBLIC_BASE_URL`).

### 3-D. 첫 결제 리허설 (운영 인증서 적용 직후, 소액·본인 카드)
공통: 시작 전 상품 재고와 판매가를 메모하고, 끝나면 테스트 주문을 취소해 재고를 원래대로 되돌린다.

| # | 시나리오 | 확인할 것 | 결과 |
|---|---|---|---|
| 1 | PC, 신용카드(일반 카드) | 승인 → 주문 `지불완료`, `PgCode=KCP`·`PgTradeNo`(=tno) 저장, 재고 차감 → **환불확정**으로 전액 취소(응답 `0000`, 재고 복원) | ☐ |
| 2 | **모바일 실기기**, 신용카드 | 카드 인증 → `/payment/kcp/return` 복귀 → 주문 완료 → 환불확정 취소 | ☐ |
| 3 | PC, 계좌이체 | 승인 → 환불확정 취소 (개발에서 미검증) | ☐ |
| 4 | **가상계좌** 발급 | 은행 선택 → 주문 `주문접수`·재고 차감, 완료 화면에 계좌·금액·입금자명·기한, 마이페이지/비회원 조회에도 표시 | ☐ |
| 5 | 가상계좌 **실제 입금** | 웹훅 수신(로그 `KCP 웹훅 수신`) → `지불완료`, `tOrdOrderPay` 의 `ReciptAmt`·`ReciptDate` 기록, 같은 통보가 **재전송되지 않음**(같은 tno 의 로그가 반복되지 않음) | ☐ |
| 6 | 입금 후 환불 | KCP 는 입금된 가상계좌를 API 로 환불하지 못한다 → 환불확정 화면이 "수동 환불 후 결제취소 호출 생략"을 안내. 은행/KCP 에서 환불한 뒤 그 옵션으로 처리 → `환불완료`, 재고 복원 | ☐ |
| 7 | 가상계좌 **미입금 만료** | `KCP_VA_EXPIRE_MINUTES` 를 짧게(예: 30) 두고 발급 → 입금 안 함 → 마감+여유 시간 뒤 계좌 사용중지·`주문취소`·재고 복원 → 설정 원복 | ☐ |
| 8 | 결제창 닫기/취소 | 주문·재고 변화 없음, 주문서 복원 | ☐ |
| 9 | 부분취소 | 2개 상품 1건 결제 후 한 라인만 환불확정 → 부분취소 금액·KCP 잔액(`rem_mny`) 확인 (개발에서 미검증) | ☐ |
| 10 | 간편결제 | 계약된 간편결제로 실결제 1건 → 즉시 취소 | ☐ |

- 5번에서 웹훅 해시가 통과하면 로그에 `hash=MATCH_PLAIN` 또는 `MATCH_WITH_KEY` 가 찍힌다. `MISMATCH` 면 403 으로 거절되어 입금이 반영되지 않고 KCP 가 재전송한다 → 검증키 값/발급 환경(운영 키인지)을 점검한다(3-G).
- 가상계좌 입금 반영은 웹훅이 **몇 분 늦게** 올 수 있다. 입금 직후 바로 안 바뀌어도 수 분 기다린 뒤 판단한다.

### 3-E. 정기 대사 (KCP)
파트너관리자 거래내역(일 단위)을 내려받아 우리 DB 와 비교한다.
```sql
-- 전일 KCP 결제 (PgTradeNo = KCP 거래번호 tno, PgOrderCode = 가맹점 주문번호 ordr_idxx)
SELECT P.OrderNo, P.PgTradeNo, P.PgOrderCode, P.PayType, P.PayAmt, P.PayDate, P.ReciptAmt, P.ReciptDate, O.OrderState
FROM shopion.tOrdOrderPay P
JOIN shopion.tOrdOrder O ON O.OrderNo = P.OrderNo
WHERE P.PgCode = 'KCP'
  AND P.PayDate >= CURDATE() - INTERVAL 1 DAY AND P.PayDate < CURDATE()
ORDER BY P.PayDate;

-- 입금 대기 중인 가상계좌(마감 임박/초과 순)
SELECT P.OrderNo, P.PgTradeNo, P.ReciptBank, P.ReciptAccnt, P.PayExpectAmt, P.PayExpectDate
FROM shopion.tOrdOrderPay P
JOIN shopion.tOrdOrder O ON O.OrderNo = P.OrderNo
WHERE P.PgCode = 'KCP' AND P.PayType = '001000000000' AND O.OrderState = '주문접수'
ORDER BY P.PayExpectDate;
```
- KCP 에 승인됐는데 우리 주문이 없다 → **결제만 된 건**: 고객 안내 후 KCP 에서 수동 취소(승인 후 주문 저장이 실패하면 자동 취소가 돌지만, 취소까지 실패하면 저장 실패 오류에 취소 실패 예외가 함께 기록된다 — 3-F).
- **카드·계좌이체 취소에는 웹훅이 없다.** KCP 관리자에서 직접 취소하면 우리 주문 상태는 바뀌지 않는다 → 대사로 찾아 환불확정 화면으로 정리하되 PG 호출은 건너뛴다(`결제취소 호출 생략`).
- 입금 대기가 마감을 한참 넘겼는데 `주문접수` 로 남아 있다 → 만료 잡이 사용중지에 실패하고 있는 것이다(3-F).

### 3-F. 수동 처리가 필요한 상황 (서버 로그 검색어)
| 로그 문구 | 의미 | 조치 |
|---|---|---|
| `수동 환불 필요` (ERROR) | 가상계좌에 입금됐지만 주문이 이미 `주문취소`/`환불완료` (만료 직후 입금 등). 자동으로 되살리지 않는다 | 입금자에게 은행/KCP 로 환불. 주문 상태는 그대로 둔다 |
| `입금액이 주문 금액과 다릅니다` (ERROR) | 부족·초과·**중복 입금**. 자동으로 `지불완료`로 바꾸지 않는다 | 입금 내역 확인 후 고객과 협의(차액 환불 또는 추가 입금). 정리되면 관리자가 주문을 수동 처리 |
| `입금 통보와 거래조회가 어긋납니다` (ERROR) | 통보는 왔는데 KCP 조회상 입금 0원 — 위조 의심 또는 KCP 지연 | KCP 관리자에서 실제 입금 여부 확인 |
| `입금 취소 통보` (ERROR) | 입금이 취소됨(`op_cd=13`). 자동으로 상태를 되돌리지 않는다 | 이미 지불완료/출고된 주문이면 출고 중단·환불 여부를 사람이 판단 |
| `가상계좌 만료 처리 실패` (WARN) | 계좌 사용중지에 실패해 주문을 취소하지 않았다. 10분마다 재시도한다 | 계속되면 KCP 관리자에서 계좌 상태 확인 후 수동 처리 |
| `입금액이 주문 금액과 달라 만료 처리하지 않았습니다` (ERROR) | 만료 점검 중 일부 금액만 입금된 것을 발견 | 위 "금액이 다릅니다"와 같다 |
| `허용되지 않은 발신 IP`, `hash_data 검증에 실패` (WARN) | 웹훅이 IP/해시 검사에서 막힘. 정상 운영 중 KCP 요청이라면 설정 오류 | 방화벽·프록시(3-C), 검증키(3-A) 점검 |
| `결제건을 찾지 못했습니다 (재전송 대기)` (WARN) | 계좌 발급 직후라 주문 저장 전이거나 다른 시스템의 거래 | 보통 재전송으로 해결. 계속되면 tno 로 주문 존재 여부 확인 |
| `KCP 자동 취소 실패` (ERROR) | KCP 가 돌려준 승인·가상계좌 발급 결과가 서버 금액·계좌와 달라 자동으로 되돌리려다 실패 | KCP 관리자에서 해당 tno 수동 취소(가상계좌는 사용중지) |
| 주문 저장 실패 오류 + 취소 실패 예외(suppressed) | 승인(또는 계좌 발급)은 됐는데 주문 저장이 실패했고 보상 취소도 실패. 응답은 오류로 나가 고객은 실패로 본다 | 해당 건의 KCP 거래를 찾아 수동 취소(대사로도 발견). 주문은 생성되지 않았다 |

### 3-G. 알려진 한계 · 미검증 (운영 첫 실결제에서 확인)
- **웹훅 해시**: 테스트 환경에는 검증키가 없어 `hash_data` 를 실제 키로 검증해 보지 못했다. KCP 문서는 검증키 사용 방식이 모호해서 두 방식(메시지만 / 메시지 끝에 `^검증키`)을 모두 허용하고, 어느 쪽이 맞았는지 로그(`hash=...`)에 남긴다.
  KCP **테스트** 통보는 `hash_data` 가 아니라 `noti_hash`(32자, HMAC-SHA256 과 다름)로 오므로 검증키를 넣은 환경에서는 테스트 통보가 403 으로 거절될 수 있다. 운영 통보의 실제 형식은 첫 입금에서 확인한다.
- **웹훅 응답 형식**: 평문 `result=0000` 에는 KCP 가 성공으로 보지 않고 약 5분마다 재전송했다. KCP 공통통보 규격(HTML, `result` hidden input)으로 응답하도록 했고 재전송이 멈춘 것은 확인했다. 운영에서도 같은 통보가 반복되지 않는지 본다(3-D 5번).
- 실통보에는 문서에 없는 `op_cd=18` 이 왔다(입금으로 처리). 문서의 50/01(입금)/13(입금취소) 외 값은 입금으로 본다.
- 개발에서 실제로 검증한 것: PC·모바일 신용카드 승인과 전액 취소, 가상계좌 발급·입금 통보 수신·만료 잡. **부분취소(`rem_mny`)·계좌이체·간편결제·모바일 계좌이체는 단위 테스트까지만**이다.
- 입금 후 환불은 KCP API 로 불가능해 **수동**이다. 미입금 가상계좌 주문은 관리자 주문취소 화면에서 취소되지 않고(대상 상태에 `주문접수` 없음) 만료 잡만 취소한다.
- 현금영수증 입력·에스크로·자동결제·휴대폰결제는 지원하지 않는다. 모바일은 웹 브라우저만(앱 WebView·외부 인증 앱 복귀 `AppUrl` 미지원).
- KCP **테스트** 모의입금 페이지(`testadmin.kcp.co.kr`)는 통보 URL 을 `http://` 로만 호출하고(https 는 통보가 오지 않음), 같은 거래에 두 번 입금하면 입금액이 누적돼 금액 불일치 안전장치가 작동한다. 테스트 때만 해당한다.

## 부록: 롤백/비상 대응
- 결제만 된 건 발견 → 토스는 대시보드, KCP 는 파트너관리자에서 수동 취소 후 고객 안내
- 설정 실수로 서비스 범위/권한이 이상할 때 → `app.authz.mode` 를 바꾸기 전에 원인(역할 SvcCode, 계정 ShopCode)을 먼저 확인하고, 임시 조치가 필요하면 한 계정만 조정
- 코드 롤백이 필요하면 직전 커밋으로 되돌리되, **재고 이력 DDL·BCrypt 로 전환된 비밀번호**는 되돌릴 수 없다는 점에 유의(구버전은 BCrypt 비밀번호를 검증하지 못하므로 전환된 고객·상점·창고 계정이 로그인 불가) — 롤백 대신 수정 배포를 권장
