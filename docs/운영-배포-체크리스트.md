# 운영 배포 체크리스트 — 실결제 검증 · 설정

> 이 문서는 "운영 반영 전 DDL/보정 SQL/토스 키 교체"(별도 목록) 외에, **실결제 경로 검증(1번)** 과 **설정 함정(2번)** 을 정리한 것이다.
> 값(비밀번호·키·호스트)은 이 문서에 적지 않는다. 환경변수/배포 설정으로만 준다.

---

## 1. 실결제 경로 검증 + 대사(정합성 확인)

### 왜 필요한가
- 토스 승인(`/order/checkout` → 토스 confirm)부터 주문 저장까지의 **전체 경로는 개발 환경에서 끝까지 돌려 보지 못했다**
  (샌드박스 key-in 결제는 바로 "완료" 상태가 되어 서버의 승인 호출이 실패한다). 단위 테스트와 부분 라이브만 검증됨.
- 승인은 됐는데 주문 저장 전에 서버가 죽거나 응답이 끊기면 자동 취소(보상)가 돌지 못해 **돈만 결제된 건**이 남을 수 있다.
  이런 건을 찾아내는 자동 대사 작업은 없다 → 아래 수동 대사를 주기적으로 한다.

### 1-A. 첫 결제 리허설 (운영 키 적용 직후, 소액 상품으로)
공통: 시작 전 해당 상품의 재고(`tPrdProd.SupplyQty`)와 판매가를 메모해 둔다.

| # | 시나리오 | 확인할 것 | 결과 |
|---|---|---|---|
| 1 | 비회원, 신용카드, 소액 상품 1개 | 결제 완료 화면 → `tOrdOrder`/`tOrdOrderProd`/`tOrdOrderPay`/`tOrdOrderPayLogToss` 각 1건, 주문상태 `지불완료`, 재고 1 감소, `tOrdOrderProdStockLog` DEDUCT 1건 | ☐ |
| 2 | 회원 로그인, 장바구니 → 2개 이상 상품(옵션 상품 포함) | 주문서의 상품금액+배송비 = 결제창 금액 = `PayAmt`, 라인별 `SalePrice`·`NvPrice`·`ReciptAmt` 가 **수량이 곱해진 합계** | ☐ |
| 3 | 선불 배송비 상품 | 배송비(상점별 최대값 합산)가 결제 총액에 포함, 라인에는 기록 안 됨(정상) | ☐ |
| 4 | 가상계좌 | 주문 `주문접수`, 재고는 즉시 차감, 입금 후 웹훅으로 `지불완료` 전환 | ☐ |
| 5 | 결제창에서 취소/닫기 | 주문·재고 변화 없음, 주문서 복원 | ☐ |
| 6 | 주문취소접수(관리자 화면) | 토스 결제 취소 + 재고 복원(+수량), 이중 취소해도 재고가 두 번 늘지 않음 | ☐ |
| 7 | 토스 대시보드에서 결제 취소(웹훅 `CANCELED`) | 배송 전 라인만 `주문취소`, 재고 복원 | ☐ |
| 8 | 재고 부족 | 재고 1인 상품을 2개 주문 → 주문서 단계에서 "재고가 부족합니다", 결제창 안 열림 | ☐ |

리허설 후: 테스트 주문은 취소(토스 취소 포함)하고 재고가 원래 값인지 확인한다.

### 1-B. 토스 웹훅 등록 확인
- [ ] 토스 개발자센터(운영 상점)에 웹훅 URL 등록: `https://<운영도메인>/payment/webhook/toss`, 이벤트 `PAYMENT_STATUS_CHANGED`
- [ ] `/payment/**` 는 로그인 없이 열려 있어야 한다(인증 제외 경로 — 이미 설정됨). 방화벽/WAF 가 토스 서버 요청을 막지 않는지 확인
- [ ] 웹훅 본문은 신뢰하지 않고 서버가 토스 API 로 결제 상태를 다시 조회한다(위조 요청으로는 상태 동기화만 일어남)

### 1-C. 정기 대사 (운영 시작 후 매일 → 안정되면 주 1회)
**목적**: 토스에서는 승인됐는데 우리 주문이 없는 건(또는 반대)을 찾는다.

1. 토스 대시보드 → 결제내역 → 전일 승인 건 내려받기(엑셀): 결제키(paymentKey), 주문ID, 금액, 상태
2. 우리 DB 의 같은 기간 결제 건을 뽑아 비교한다:
```sql
-- 전일 스토어프론트 결제 (PgTradeNo = 토스 paymentKey, PgOrderCode = 토스 orderId)
SELECT P.OrderNo, P.PgTradeNo, P.PgOrderCode, P.PayAmt, P.PayDate, O.OrderState
FROM shopion.tOrdOrderPay P
JOIN shopion.tOrdOrder O ON O.OrderNo = P.OrderNo
WHERE P.PgCode = 'TOSS'
  AND P.PayDate >= CURDATE() - INTERVAL 1 DAY AND P.PayDate < CURDATE()
ORDER BY P.PayDate;
```
3. 판정
   - 토스에 있고(상태 DONE) DB 에 없다 → **결제만 된 건**: 고객에게 안내 후 토스에서 수동 취소(또는 주문 수기 등록)
   - DB 에 있고 토스에는 취소(CANCELED)로 되어 있는데 주문 상태가 `주문취소`/`환불완료`가 아니다 → 웹훅 누락: 해당 건의 취소 처리
   - 금액 불일치 → 즉시 원인 확인(정상이라면 발생하지 않음 — 서버가 금액을 계산·검증한다)
4. 로그: `주문 저장 실패로 인한 자동 취소` 가 호출된 건은 서버 로그에서 확인(저장 실패 → 자동 취소 정상 동작 사례)

### 1-D. 이상 징후 모니터링 쿼리
```sql
-- 결제는 됐는데(지불완료) 라인이 비어 있는 주문
SELECT O.OrderNo FROM shopion.tOrdOrder O
LEFT JOIN shopion.tOrdOrderProd OP ON OP.OrderNo = O.OrderNo
WHERE O.OrderState = '지불완료' AND OP.OrderNo IS NULL;

-- 재고가 음수가 된 상품(샵링커/상품매칭은 초과 차감 허용 — 스토어프론트는 막힘)
SELECT ProdCode, ProdName, SupplyQty FROM shopion.tPrdProd WHERE SupplyQty < 0;

-- 차감 이력은 있는데 주문 라인이 없는 이력(롤백 누락 징후 — 정상이면 0건)
SELECT L.OrderNo, L.OrderProdNo FROM shopion.tOrdOrderProdStockLog L
LEFT JOIN shopion.tOrdOrderProd OP ON OP.OrderNo = L.OrderNo AND OP.OrderProdNo = L.OrderProdNo
WHERE OP.OrderNo IS NULL;
```

### 1-E. 운영 시작 방식 권장
- 첫 주는 저가 상품/소수 고객으로 시작, 매일 1-C 대사 수행
- 첫 정산 마감은 소량 상점·짧은 기간으로(마감은 앱에서 되돌릴 수 없음)

## 2. 설정 함정 (배포 설정)

### 2-A. 필수 환경변수 / 설정
| 항목 | 설정 | 안 하면 |
|---|---|---|
| 프로파일 | `SPRING_PROFILES_ACTIVE=prod` (기본값은 `dev`) | MyBatis **DEBUG 로그에 SQL 파라미터·고객정보** 가 찍힘, 템플릿 캐시 꺼짐, 커넥션 풀 10 |
| `DB_HOST`, `DB_PASSWORD` | 배포 설정으로 주입(저장소에 없음) | 기동 실패 |
| `SESSION_COOKIE_SECURE` | HTTPS 서비스면 `true` (기본 `false`) | 세션 쿠키가 HTTP 로도 전송됨 |
| `TOSS_SECRET_KEY` | **운영 시크릿 키** (기본값은 테스트 키) | 미설정 시 **조용히 테스트 키로 동작** → 운영 결제 승인 실패/혼선 |
| `shop.html` 의 `TOSS_CLIENT_KEY` | **운영 클라이언트 키로 코드 수정**(HTML 에 직접 박혀 있음, 환경변수 아님) | 서버 키만 바꾸면 결제창/승인 키 불일치 |
| `UPLOAD_DIR` | 영구 저장소의 **절대경로** (기본 `uploads` 는 실행 위치 기준 상대경로) | 서버 위치가 바뀌면 이미지가 사라진 것처럼 보임, 백업 대상 누락 |
| `SHOP_CHNL_CODE` | 운영 DB 의 스토어프론트 채널코드 (기본 `1208674775Z2`) | 주문이 엉뚱한 채널로 저장 |
| `SHOPLINKER_*` | 필요 시(기본값은 운영 주소 http) | — |

### 2-B. 권한·보안 설정
- [ ] `app.authz.mode` 는 기본 `enforce` — **`off`/`log` 로 바꾸지 말 것**(off 면 역할 권한·데이터 범위 검사가 모두 꺼짐)
- [ ] HTTPS 종단(리버스 프록시/로드밸런서) 사용 시 클라이언트 IP 전달 확인 — 로그인 시도 제한 키가 (종류+아이디+접속 IP)인데 앱은 `getRemoteAddr()` 를 쓰고 `server.forward-headers-strategy` 가 설정돼 있지 않다.
      프록시 뒤에서 모든 접속이 같은 IP 로 보이면, 특정 아이디에 대한 실패 시도가 **그 아이디의 모든 사용자를 잠글 수 있다**. 프록시를 쓰면 `server.forward-headers-strategy=native`(또는 framework) 설정을 검토
- [ ] 배포 후 **전체 권한 계정(시스템 관리자)은 재로그인** — 서비스 범위 제한이 들어가면서 기존 세션은 제한이 걸린 상태로 보임
- [ ] 기존 로그인 중이던 관리자/고객 세션은 서버 재시작 시 모두 끊김(세션이 서버 메모리) → 사용량이 적은 시간대에 배포

### 2-C. 운영 환경 특성
- [ ] **서버는 1대 기준**: 세션, 로그인 시도 제한, 샵링커 수집 중복 실행 방지가 서버 메모리. 2대 이상이면 세션 공유(sticky/세션 저장소)와 수집 단일 실행 보장이 필요
- [ ] 업로드 이미지 디렉터리 쓰기 권한/용량/백업, 이미지 URL 은 `/images/**`
- [ ] 샵링커 주문수집 API 는 `http://` (제공 측 사양) — 서버에서 해당 호스트로 나가는 방화벽 허용 확인
- [ ] 운영 DB 사전 점검: 별도 목록(DDL `tOrdOrderProdStockLog`, 옵션가 NULL 보정 SQL, 정산 컬럼 존재 확인)
- [ ] 기동 로그에 `spring.profiles.active=prod` 가 보이는지, 로그에 SQL 파라미터가 안 찍히는지 확인

### 2-D. 배포 직후 스모크 테스트 (10분)
- [ ] 관리자 로그인 → 사이드바 메뉴가 역할대로 보임(시스템 관리자 전체, 업체담당자 제한)
- [ ] 주문관리 화면 조회(기간 지정), 판매 상품 관리 조회
- [ ] 업체담당자 계정으로 로그인 → 자기 상점 주문만 보이는지
- [ ] 스토어프론트: 상품 목록 → 상세 → 바로구매 → 주문서 금액 표시 → (소액 결제는 1-A 리허설로)
- [ ] 고객 로그인(기존 고객 1명) — 첫 로그인 때 비밀번호 해시가 BCrypt 로 자동 전환됨(`tPrfCust.Passwd` 가 `$2` 로 시작)
- [ ] 서버 로그에 ERROR/WARN 폭주가 없는지

## 부록: 롤백/비상 대응
- 결제만 된 건 발견 → 토스 대시보드에서 수동 취소 후 고객 안내
- 설정 실수로 서비스 범위/권한이 이상할 때 → `app.authz.mode` 를 바꾸기 전에 원인(역할 SvcCode, 계정 ShopCode)을 먼저 확인하고, 임시 조치가 필요하면 한 계정만 조정
- 코드 롤백이 필요하면 직전 커밋으로 되돌리되, **재고 이력 DDL·BCrypt 로 전환된 비밀번호**는 되돌릴 수 없다는 점에 유의(구버전은 BCrypt 비밀번호를 검증하지 못하므로 전환된 고객·상점·창고 계정이 로그인 불가) — 롤백 대신 수정 배포를 권장
